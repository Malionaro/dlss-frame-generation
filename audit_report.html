1. Wie sieht es mit dem Projekt aus? (Executive Summary)

Architektur-Review

🌟 Wo das Projekt herausragend ist

  • Brillante Hybrid-Architektur: Die Verbindung von Mojang's modernem VulkanDevice mit NVIDIA Streamline 2.12 und AMD FidelityFX FSR 3.1 über eine Win32-Shared-Handle-D3D12-Präsentationsbrücke ist ein ingenieurtechnisches Meisterwerk.
  • Echte Zero-Copy Pipelines: NV12/RGBA Cross-API Texture Sharing via VK_KHR_external_memory_win32 und Shared Fences minimiert VRAM-Kopien.
  • Solide Testabdeckung: 62 JUnit-5-Tests sichern Presets, Fallback-Ketten, Motion-Vector-Normalisierung und Config-Sanitization ab.
  • All-in-One Packaging: Die Mod bündelt alle benötigten Streamline-Plugins, OptiScaler 0.9.4 und FidelityFX-Bibliotheken direkt im JAR (141.5 MB).
  • Native Kompilation verifiziert: Der MSVC C++20 Build erzeugt die dlss_fg_native.dll nun sauber in 44 Sekunden.

⚠️ Wo die größten Risiken & Flaschenhälse liegen

  • 3ms CPU Spin-Wait pro Frame: Auf dem Render-Thread laufen in VulkanGpuSurfaceMixin und VulkanFrameGenerationPipeline künstliche Spin-Wait-Schleifen, die bis zu 40% des Frame-Budgets bei 120+ FPS verheizen.
  • Mutex-Disziplin in WindowsDxgiPresenter.cpp: Manuelles g_mutex.unlock() unter einem aktiven std::lock_guard während 10-Sekunden-Queue-Idle-Waits hebelt den Thread-Schutz aus.
  • Marker Fence vor Render-Submit: Im RT-Renderer wird der Marker-Fence submitted, bevor Minecraft seinen Frame-Command-Buffer einreicht (Inverted Order).
  • Externer OptiScaler-Override gesperrt: OptiScalerIntegration verifiziert externe DLLs gegen den Hash der internen 0.9.4 DLL, wodurch neuere Versionen abgewiesen werden.
  • Fehlende Multi-GPU Hardware-Validierung: Echte Live-Tests auf Radeon RX 7000 (FSR 3.1 Pacing) und Intel Arc (XeSS-FG) stehen noch aus.

3. Gefundene Fehler & Schwachstellen (Deep Scan Findings)

Code Audit
BUG-01 KRITISCH / PERFORMANCE Render-Thread 3ms CPU Spin-Wait Burn pro Frame
VulkanGpuSurfaceMixin.java:404 & VulkanFrameGenerationPipeline.java:624

Problembeschreibung:

In VulkanGpuSurfaceMixin.java (Zeilen 404–407) und VulkanFrameGenerationPipeline.java (Zeilen 624–628) existieren harte Spin-Wait Schleifen mit Thread.onSpinWait(): 

// VulkanGpuSurfaceMixin.java:404-407
if (!gpuIdleConfirmed) {
    long spinDeadline = System.nanoTime() + 2_000_000L; // 2 MILLISEKUNDEN!
    while (System.nanoTime() < spinDeadline) {
        Thread.onSpinWait();
    }
}

// VulkanFrameGenerationPipeline.java:624-628
if (!gpuIdleConfirmed) {
    long spinDeadline = System.nanoTime() + 1_000_000L; // 1 MILLISEKUNDE!
    while (System.nanoTime() < spinDeadline) {
        Thread.onSpinWait();
    }
}

Auswirkung:

Da gpuIdleConfirmed im normalen Spielbetrieb standardmäßig false ist (weil strictSync standardmäßig false ist), verbringt der Render-Thread auf jedem einzelnen Frame exakt 3 Millisekunden in einer 100% CPU-Last-Spinning-Schleife. Bei einem Frame-Budget von 8.33 ms (120 FPS) verbrennt die Mod 36% der gesamten Frame-Zeit sinnlos!

BUG-02 KRITISCH / CONCURRENCY Inkorrektes Mutex-Unlocking unter std::lock_guard & Deadlock-Gefahr
WindowsDxgiPresenter.cpp:307 & 1278

Problembeschreibung:

In native/bridge/presentation/WindowsDxgiPresenter.cpp ruft releasePresentationLocked() (Zeile 307) direkt g_mutex.unlock() und g_mutex.lock() auf, um während des bis zu 10 Sekunden dauernden waitForD3D12QueueIdle() den Mutex freizugeben. Allerdings rufen Aufrufer wie createSwapchain() (Z. 1023), destroySwapchain() (Z. 1174) und shutdown() (Z. 1387) diese Funktion unter einem aktiven std::lock_guard lock(g_mutex) auf! 

// WindowsDxgiPresenter.cpp:307
void releasePresentationLocked() {
    g_mutex.unlock(); // GEFÄHRLICH: lock_guard hält die Sperre weiterhin für sich!
    waitForD3D12QueueIdle(); // Wartet bis zu 10.000 ms!
    g_mutex.lock();
    ...
}

Auswirkung:

1. Das manuelle Freigeben und erneute Anfordern bricht die Invariante von std::lock_guard.
2. Während der 10 Sekunden Wartezeit können andere Threads in die Swapchain-Funktionen eintreten und halb zerstörte D3D12-Pointer lesen (Access Violation 0xC0000005).
3. In queuePresent() (Z. 1345) wird g_dxgiSwapchain->Present() mit gehaltenem Mutex aufgerufen. Bei aktiviertem VSync blockiert dies alle anderen Status- und Diagnose-Threads bis zum nächsten VBlank.

BUG-03 HOCH / GPU SYNC Invertierte Marker-Fence-Reihenfolge in VulkanRayQueryRenderer
VulkanRayQueryRenderer.java:157 & 1383

Problembeschreibung:

In VulkanRayQueryRenderer.java wird zur Synchronisation der Slot-Uniform-Buffer eine leere Marker-Befehlssequenz (slotMarkerCommandBuffers) per vkQueueSubmit an die Queue gesendet. Allerdings geschieht dies während Minecraft noch den Frame-Befehlspuffer aufzeichnet!

Dadurch wird der Marker-Fence vor dem eigentlichen Render-Befehlspuffer in die Queue eingereiht. Auf der GPU signalisiert der Fence als "fertig", bevor Minecrafts Renderbefehle überhaupt ausgeführt wurden! Folge: Der Uniform-Buffer wird im Ring 3 Frames später überschrieben, während die GPU noch die vorherigen Daten liest (Raytracing-Ghosting und fehlerhafte Schatten).

BUG-04 HOCH / INTEROP Externer OptiScaler-Override durch Hardcoded 0.9.4 Hash blockiert
OptiScalerIntegration.java:205

Problembeschreibung:

In OptiScalerIntegration.java (Zeile 205) wird ein externer Benutzer-Override in config/dlss_fg/optiscaler/OptiScaler.dll gegen die Map EMBEDDED_SHA256 geprüft: 

verifyEmbeddedHash(externalDll, "OptiScaler.dll");

Da EMBEDDED_SHA256 fest auf den Hash von OptiScaler 0.9.4 verdrahtet ist, schlägt die Verifikation für jede neuere Version (z. B. 0.9.5 oder ein Nightly-Build) zwingend fehl. Die Mod fällt immer auf die integrierte Version zurück. Der externe Override ist damit de facto unbrauchbar.

BUG-05 MITTEL / RESOURCE LEAK Windows DLL Locking verhindert deleteOnExit()
NativeLoader.java:64 & 90

Problembeschreibung:

Unter Microsoft Windows verhindert der Betriebssystem-Kernel das Löschen von DLL-Dateien, die derzeit von einem aktiven Prozess via LoadLibrary (bzw. System.load) geladen sind. File.deleteOnExit() scheitert beim Beenden der JVM stillschweigend. Erst nach 24 Stunden räumt cleanupOldTempDirs() alte Verzeichnisse auf. Bei häufigen Neustarts sammeln sich hunderte Megabyte in %TEMP%\dlss_fg_natives-* an.

4. Konkrete Lösungsideen & Code-Fixes

Implementation Recipes

Fix 1: Beseitigung der Render-Thread 3ms CPU Spin-Waits

Konzept: Anstelle eines busy CPU-Spin-Waitings wird eine ringbasierte Slot-Verwaltung (3–4 Slots) genutzt. In Vulkan garantiert ein Triple-Buffering-Ring bei regulärem Present eine natürliche Pufferung, ohne dass der Render-Thread schlafen oder spinnen muss. 

// VORHER (VulkanGpuSurfaceMixin.java:404):
- if (!gpuIdleConfirmed) {
-     long spinDeadline = System.nanoTime() + 2_000_000L;
-     while (System.nanoTime() < spinDeadline) { Thread.onSpinWait(); }
- }

// NACHHER: Non-blocking Slot-Advancement ohne CPU-Spin
+ // Ring of 3 frame slots guarantees that slot (current - 2) is already retired by the GPU
+ // No manual spin-wait needed on the render thread!
+ if (frameGenerationPipeline != null) {
+     frameGenerationPipeline.markPresentDispatchedNonBlocking();
+ }

Gewinn: Sofortige Einsparung von 3.0 ms Frame-Zeit pro Frame (bis zu +40% FPS-Kapazität auf dem Render-Thread).

Fix 2: Mutex-Disziplin & State-Machine in WindowsDxgiPresenter.cpp

Konzept: Konsistente Verwendung von std::unique_lock<std::mutex>. Während Present() und waitForD3D12QueueIdle() wird der Mutex explizit über unique_lock freigegeben, nachdem der Zustand atomar auf Stage::TearingDown bzw. Stage::Presenting gesetzt wurde. 

// VORHER (WindowsDxgiPresenter.cpp:307):
- void releasePresentationLocked() {
-     g_mutex.unlock();
-     waitForD3D12QueueIdle();
-     g_mutex.lock();
- }

// NACHHER (Saubere unique_lock State-Machine):
+ void releasePresentation(std::unique_lock<std::mutex>& lock) {
+     g_stage = Stage::TearingDown;
+     // Mutex sicher freigeben während des langen Queue-Waits
+     lock.unlock();
+     waitForD3D12QueueIdle();
+     lock.lock();
+     // Ressourcen freigeben unter wiedererlangter Sperre
+     releasePresentationResourcesUnderLock();
+     g_stage = Stage::Uninitialized;
+ }

Fix 3: Inline vkCmdUpdateBuffer für Raytracing-Uniforms

Konzept: Statt über separate Marker-Fences zu synchronisieren, werden die ~112 Bytes des FrameParameters-Uniform-Buffers direkt über vkCmdUpdateBuffer(commandBuffer, ...) in Minecrafts aktiven Command Buffer geschrieben. 

// Inline Vulkan-Update garantiert Ausführung exakt vor dem Compute-Dispatch:
+ ByteBuffer nativeData = frame.toNativeBuffer();
+ VK13.vkCmdUpdateBuffer(
+     commandBuffer,
+     uniformBuffers[frameSlot],
+     0L,
+     nativeData
+ );
+ // Memory Barrier zwischen Transfer-Write und Uniform-Read im Compute-Shader:
+ recordBufferMemoryBarrier(commandBuffer, uniformBuffers[frameSlot]);

Gewinn: 100% frei von Fences, kein CPU-Spin-Wait, keine Überholungsgefahr im GPU-Scheduler.

Fix 4: Flexible Signatur-/Prüfsummen-Tabelle für OptiScaler

Konzept: Eine known-hashes.json oder Zulassung von externen DLLs mit Benutzer-Warnung (Warn-Log statt hartem Fallback), wenn der Entwickler explizit eine neue OptiScaler-Version in config/dlss_fg/optiscaler/ ablegt. 

// VORHER: Schlägt bei jedem Versionsupdate fehl:
- verifyEmbeddedHash(externalDll, "OptiScaler.dll");

// NACHHER: Unterstützt bekannte Hashes & warnt bei Custom-DLLs:
+ if (isKnownOptiScalerHash(externalDllHash)) {
+     logger.info("[OptiScaler] Verified official release: {}", externalDllHash);
+ } else {
+     logger.warn("[OptiScaler] Custom/unverified OptiScaler build detected (SHA: {}). Loading as configured by user.", externalDllHash);
+ }
